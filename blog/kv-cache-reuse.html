Reusing the KV cache

2026.08.20 · Hyeondo Jang

A KV cache is usually introduced as a within-request optimization: keep the keys and values of the tokens you have already seen so decode does not redo them. But the same entries are often valid for the next request too, and for the request after that. This post is about when that is true, why it is true, and what it costs to exploit.

1The invariant that makes reuse legal

Decode reads the cache; it never rewrites it. At step t the model forms one query per head for the new token and attends over keys and values that were written at steps $1,\dots,t-1$, and those earlier entries are never touched again — that is the whole point of keeping them.

That alone does not license reuse across requests. Reuse needs a stronger claim: that an entry is determined by the tokens before it and by nothing else. It is, and the reason is that exactly one stage in the stack moves information between positions.

Every other stage is row-wise. RMSNorm rescales each row on its own, the feed-forward network maps row i to row i, and the residual adds line up position by position:

\begin{equation} \big[\RMSNorm(\mat{X})\big]_i = \RMSNorm(\vect{x}_i), \qquad \big[\FFN(\mat{X})\big]_i = \FFN(\vect{x}_i) \end{equation}

Attention is the exception, and the causal mask makes it a one-directional one. Row i of the attention output is a weighted average of value rows at positions $j \le i$, with no term beyond $i$ at all:

\begin{equation} \big[\Attn(\mat{Q},\mat{K},\mat{V})\big]_i \;=\; \sum_{j=1}^{i} \alpha_{ij}\,\vect{v}_j, \qquad \alpha_{ij} \;=\; \frac{\exp\!\big(\vect{q}_i\T\vect{k}_j/\sqrt{\dhead}\big)} {\sum_{j'=1}^{i}\exp\!\big(\vect{q}_i\T\vect{k}_{j'}/\sqrt{\dhead}\big)} \end{equation}

Now induct over the $\nlayer = 36$ blocks. Row i of $\mat{X}^{(0)}$ is the embedding of $t_i$, so it is a function of $t_i$ alone. If rows $1,\dots,i$ of $\mat{X}^{(\ell-1)}$ are functions of $t_1,\dots,t_i$, then attention at block $\ell$ pulls in only those rows and every other stage stays on row i, so the same holds at block $\ell$:

\begin{equation} \vect{x}^{(\ell)}_i \;=\; f^{(\ell)}_i(t_1,\dots,t_i), \qquad \ell = 0,1,\dots,\nlayer \end{equation}

The keys and values are row-wise linear maps of that row, followed by a rotation $\Rope_i$ that depends only on the position index:

\begin{equation} \vect{k}^{(\ell)}_i = \Rope_i\!\big(\vect{x}^{(\ell-1)}_i \mat{W}^{(\ell)}_K\big), \qquad \vect{v}^{(\ell)}_i = \vect{x}^{(\ell-1)}_i \mat{W}^{(\ell)}_V \end{equation}

So every cache entry inherits the same dependency. Write $\KVc_{1:S}$ for the first $S$ entries of the cache, across all layers and heads. The cache is prefix-closed:

\begin{equation} \KVc_{1:S}\big(t_{1:T}\big) \;=\; \KVc_{1:S}\big(t_{1:S}\big) \qquad\text{for every } S \le T \end{equation}

Read it right to left. The cache you get by prefilling only the first $S$ tokens is exactly the first $S$ entries of the cache you get by prefilling all $T$ of them. Adding tokens on the right changes nothing on the left. Two requests that begin with the same $S$ tokens therefore hold the same first $S$ entries — not approximately, the same numbers — and the second one can read what the first one already wrote.

The reuse invariant

The KV cache is a pure, prefix-closed function of the token ids. Everything that follows is an engineering answer to a single question: how do you cheaply find and address the part of a cache you already have?

Note what the invariant does not say. It is a statement about prefixes, and it runs one way only. A chunk of tokens sitting in the middle of a prompt is not a function of itself — it is a function of itself and everything to its left. Lift a document out of one prompt and drop it into another and its cached entries are wrong, because they encode attention to a left context that is no longer there, at positions it no longer occupies. Section 4 makes both failures precise; section 5 asks what can be salvaged.

One more caveat, which is about arithmetic rather than mathematics. Equality here holds exactly in $\R$, and only approximately in floating point: prefilling $T$ tokens and prefilling $S < T$ tokens can choose different kernel tilings and reduction orders, so a reused entry may differ from a recomputed one in the last few bits. Serving stacks accept this. It is the same class of nondeterminism you already get from changing the batch size.
